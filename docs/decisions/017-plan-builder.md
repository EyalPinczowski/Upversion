# 017 – Plan builder v1: a rule-based plan from profile, target role, time and deadline

**Status:** Accepted (owner, 2026-11-12). Every question in section 9 is now owner-decided: Q1 (AI explanations in v1), Q3 (archive the old active plan), Q8 (unverified items chosen without a link), Q11 (no `exam_minutes`; 2 h default), Q12 (USD-only budget limits), Q13 (read-only and restore rules of 4.1), and the recommended defaults Q2, Q4, Q5, Q6, Q7, Q9 and Q10. Amends ADR 004 and ADR 007 (section 8).

Builds on ADR 001 (pure scheduling), 004 (AI optional, rule-based builder is the default), 007 (catalog-grounded generation), 012 (`AIProvider`), 015 (setup answers, `user_profiles`, CV import) and 016 (Change my CV, `matchSkillsInText`, `keywordGaps`). Implements the core of spec 3.0 ("Plan builder – from goal to plan"). Read on `rnd` at `c9b4f21` (2026-11-12).

## Context
- Spec 3.0 describes the full builder: a 28-question intake, RAG retrieval, an AI that chooses and orders catalog items, "Make this plan free", regenerate, conversational mode, user-added catalog items. None of it is built. Plans today come only from `POST /api/v1/plans/import` (a hand-made plan file, like the owner's own plan and `data/sample-plans/demo-plan.json`).
- What already exists and is reused: setup answers and `profile.skills` with `source` (`cv`/`setup`/`manual`) in `user_profiles` (ADR 015); `matchSkillsInText` for a pasted job post (ADR 016 §5); the plan file format (`PlanFileSchema`, `parsePlanFile`), `TaskSourceSchema` already has `builder`, `plans.created_from` already allows `builder`; the scheduling engine `schedule()`; the demo plan's conventions (`externalRef: "catalog:<id>"`, no `url` and a "Needs check" note when a link or price is not verified, exam split into prep + exam block, admin tasks for booking).
- The catalog lives only as bundled JSON (`data/catalog/*.json`; `schema.sql` is a reference, no catalog migration exists). `roles.json` has weighted skills (1–5) and `suggested_path` (`core`/`optional`/`practice`/`free_only`) per role.

## Options
1. **Spec 3.0 in full, AI first** (RAG + model orders the plan, rules as fallback). Needs embeddings, a catalog in the database and a new AI purpose; large, and the AI-off path would be the second-class one.
2. **Deterministic builder first, AI only for explanation text, behind a flag.** The same pure function runs with AI on or off; the plan is always identical for identical inputs.
3. **Web-only builder** that produces a plan file and posts it to `/plans/import`. Breaks spec 12.3 ("no business logic in the frontend") and spec 3.0 ("cost is recalculated by the backend").

## Decision
Option 2. A pure shared function `buildPlan(input, catalog)` makes the draft; the API runs it (preview, then create on confirm); the web only renders and collects choices. AI never chooses, adds, orders or prices items. The parts of 3.0 not in this record (RAG, catalog in the database, user-added catalog items, conversational intake, "regenerate with an instruction", quick check, "Make this plan free" side-by-side) stay for later records; none is a 12.1 deferred feature, so this is ordering, not a scope change.

### 1. Inputs and UX
**Where:** a new page `/plan/new` ("Build a plan"), shown only when `features.planBuilder` is true. Entries: the no-plan state of the Plan page (next to "Import a plan file"), a "Build a new plan" button on the Plan page, and the setup Done step ("Build my first plan"). Blocks design, no gradients, no nested cards, no decorative emoji; usable at 360 px; axe clean.

**Steps** (progress "Step n of 5", Back on every step, answers kept in component state; not saved to the server until step 5):
1. **Target.** Role picker from `roles.json` (1–2, pre-filled from `profile.answers.target_role`) and extra skills from `skills.json` (at most `target_skills.max` from `questions.json`, today 5; pre-filled from `target_skills`). Optional "Paste a job post": matched **in the browser** with `matchSkillsInText`; detected skills are shown as checkboxes for confirmation. Since ADR 016's 2026-11-12 decision the matcher also returns `terms` (the post's own wording, at most 3 per skill); each checkbox shows the catalog skill name with those words as a hint ("SQL – \"SQL queries\""), but only the confirmed skill ids are sent. The post text and its `terms` are never sent or stored.
2. **Your skills.** The `skill_levels` matrix (scale from `questions.json`) for the union of the target role skills and extra skills. Pre-filled from `profile.skills` (each row shows its source: "from your CV", "from setup", "you set this"); unknown rows start at "Never used" and are labelled "not rated". A link "Change my CV" (ADR 016 §1, `/settings/cv`) returns here. Edits here are used for this plan only. Saving them back to the profile is **not in v1**: no profile endpoint writes single skills with `source: 'manual'` today (ADR 015 has only `answers` and the CV `import`); it is a later item.
3. **Time.** Start date (default: tomorrow), deadline (date, or weeks; default from `timeframe.default_weeks` = 4), study days and hours per day (pre-filled from `days_per_week` / `hours_per_day`), window from `time_of_day` (mapping in WP-1), time zone from the browser. No live hours line here: whether the plan fits comes from the preview, which runs the real engine (section 2, step 9).
4. **Budget and certificates.** `budget` (free / limit with an amount / flexible) and `max_item_price` (rules in section 2, step 10), `certificates` (must / nice / none), `interview_prep` (yes / later / no). All rendered from `questions.json`, never hard-coded.
5. **Draft review** (the "Here's what I understood" summary plus the draft). Top summary: total hours vs capacity, projected finish date, cost vs limit (with "+ prices to check"), certificates, skills covered vs asked, and gaps the catalog cannot fill. Then the item list (core, then optional), each with hours, cost, a "why this is here" line, badges ("Needs check: link", "Needs check: price", "Price varies – check") and controls: remove, core/optional, and for exams "Include this exam" (opt-in). A "Certificates you can add" list shows the matching exams not included. Every change re-runs the preview. **"Start this plan"** creates it; nothing is created before that (spec 3.0 step 3, 12.2). When the user already has an active plan, pressing it first opens a confirm dialog: "Your current plan **<name>** will be archived. You can still open it read-only, and restore it later from the plan list." with "Archive it and start" / "Cancel" (section 4.1).

### 2. Algorithm (`buildPlan`, pure, deterministic, no I/O, no `Date.now()`)
Inputs: `BuildRequest` (section 4) + the bundled catalog + `today` (the current date in the request's `weekPattern.timezone`, computed by the API, as the schedule route does). Output: `BuildDraft` = a valid `PlanFile` plus per-item metadata, summary and warnings.

1. **Targets.** For each target role skill: `need = 2` (Comfortable) if weight ≥ 4, else `1`; extra skills: `need = 2`. `gap = max(0, need − level)`; `priority = weight × gap` (extra skills weight 4). Skills with `gap = 0` are listed as "already covered".
2. **Eligible items.** Catalog items of type `course` or `cert_exam` that teach a gap skill, with a non-null `url` (items with `url: null` are never chosen, as `build.py` already does for role paths). Item budget filter (section 2, step 10): `free` → `cost_type` `free` or `free_audit` (certificate not bought); with `max_item_price` → known price ≤ it; `price: null` excluded unless `flexible` (then shown as "Price varies – check"). Items in the request's `exclude` list are dropped.
3. **Selection (greedy set cover).** Score each eligible item: Σ priority of the uncovered gap skills it teaches + 3 if in a target role's `suggested_path.core` (or `free_only` when budget is free) + 1 if `url_verified` − 1 if `level` is `beginner` and the user's level on all its skills is ≥ 1 (and an `intermediate` item covers the same skills). Pick the highest, mark its skills covered, repeat until every gap skill is covered or no item helps. Ties break by catalog id. `cert_exam` items are not chosen here (step 5). `mustInclude` ids are added first.
4. **Prerequisites.** Add every transitive `required` prerequisite (of courses, exams and practice items), except one whose skills the user rated ≥ 2 (listed as "skipped: you rated X Comfortable"). The skip applies to prerequisites of courses and practice items only: **an exam's prerequisites are never skipped by profile level** (a provider may require them). Closure-added items pass the same budget filter; if a required prerequisite fails it (or has `url: null`), the item that needs it is dropped and reported ("needs <title>, which is outside your budget"), never added around the filter. `recommended` edges only order items already in the plan.
5. **Certificates.** Candidate exams = `cert_exam` items teaching a target skill, within budget. `must` → the best-scoring candidate per target role is included and the rest offered; `nice` → none included, all offered; `none` → none offered. The user's opt-ins (`certificateOptIns`) are included. Exam tasks (owner decision Q11: no catalog field, the exam block is at most 2 h and says "Needs check: exam length – see the provider's page"): if `est_hours ≤ 2` (e.g. `psm-1`, the HackerRank tests) one "X – exam" task of `est_hours`; otherwise "Prepare for X" (`course`, splittable, `max(1, est_hours − 2 − Σ est_hours of X's required course prerequisites already in the plan)`) and "X – exam" (2 h). The exam task is `cert_exam`, `splittable: false`, `isCertificate`; each exam also gets "Book the X exam" (`admin`, 0.25 h, before the exam). A required prerequisite that is itself an exam (`hackerrank-sql-intermediate` needs `hackerrank-sql-basic`) is included as its own exam with its own booking and cost, is not subtracted from the preparation, and the later exam depends on it. A `free_audit` item's paid certificate is opted into through the same `certificateOptIns` list (its catalog id), which adds `certificate_price` to the cost and sets `isCertificate`. An exam date from `examDates` makes the exam an anchor (`isAnchor`, `anchorDate`, `anchorStartTime`).
6. **Practice.** `interview_prep` yes/later → the target role's `suggested_path.practice` items (≤ 4). Practice templates are run in the app, so they are allowed with `url: null` (26 of 27 have none); the `url` rule of step 2 does not apply to them; "later" makes them depend on the last course. Practice for a skill always comes after the learning items for that skill (learn-before-practice, README "Structure fields").
7. **Admin.** "Set up learning accounts" (0.5 h, first) and a "Weekly review" (0.5 h) after roughly every week of planned hours. Fixed template text, no catalog link. **No `cv_update` tasks:** the tasks module creates them when a certificate is completed (spec 3.6).
8. **Order.** Topological sort over prerequisite and learn-before-practice edges; ties by core before optional, then priority, then catalog id. `order` = position; `dependsOn` = prerequisite, booking and practice edges only (so the engine can interleave).
9. **Fit.** Run `schedule()` on the draft (pattern, window, lunch, breaks and minimum block all apply; no calendar busy time, which is applied after creation as today). It fits when `finishDate ≤ deadline` and no engine warning says a task could not be placed. Σ `dayCapacity` is not used: it ignores the window and breaks. If it does not fit: drop optional items one at a time (lowest priority first), re-running `schedule()` each time; if still not, return `fits: false` with the three spec options computed by the engine: "finish on <date>" (the unconstrained `finishDate`), "study <h> hours a day" (the smallest `defaultHours` on a 0.5 h grid that fits, found by binary search between the current value and the window length, so at most about 6 engine runs; "not possible within your window" if even the window length does not fit), "keep only the essentials" (drop lowest-priority core items until it fits, listing the skills lost). The builder never applies one silently.
10. **Cost.** One-time prices summed; a `subscription_group` is paid once per month it is used (months = ceil((last − first + 1 days of the group's scheduled blocks) / 30), at least 1); a subscription without a group counts its own period; `free_audit` costs 0 (its `certificate_price` only if the user opts into the certificate). `price: null` is not added; the summary says "+ N prices to check". Any item with `price_verified: false` makes the total "estimated". **Budget rules (owner, Q12):** `free` → no paid item or paid certificate. `limit` → an amount is required (the schema answers 400 without one; the web asks for it) and the **total** known cost must be ≤ that amount (spec section 9: "Price limit $100 → the backend-calculated total is ≤ $100"); `max_item_price`, if given, is a per-item cap on top. `flexible` → no total cap; `max_item_price` still applies if given. Currency: `questions.json` offers USD, ILS and EUR, but every catalog price is USD and the app has no exchange rate (none may be invented), so in v1 the limit is entered and compared in USD, the ILS and EUR choices are not offered, and the budget step says "Catalog prices are in US dollars" (owner, Q12). Over the total: swap a paid item for its first `free_alternative_ids` entry that teaches the same gap skills, else drop optional items, else drop lowest-priority core items and list the skills lost; it never silently exceeds the limit. **Order:** item budget filter (steps 2 and 4) → selection → fit (step 9) → total cost on the fitted schedule (subscription months depend on it) → if over the total, one swap/drop pass, then **one** re-fit and cost check; if it is still over after that bounded loop, the draft is returned with `overBudget: true` and the items to remove, never looped again.
11. **Task mapping.** id `c-<catalogId>` (`p-`/`x-`/`b-` for prep/exam/booking, `a-<kind>-<n>` for admin); title, provider from the catalog; **`url` only when `url_verified: true`**; `externalRef: "catalog:<id>"`; `source: 'builder'`; `isCertificate` and `certificateName` when `certificate_type` is not `none`; `notes` = generated "why" line + "Needs check: link not yet verified…" / "Needs check: price not verified." / "Price per catalog: N USD (prices change; re-check before paying)" only when `price_verified`. Plan `name` = "<role title> plan" (catalog text only); `skillIds` = target skill ids (feeds the briefing's podcast pick); `endDate` = deadline.
12. **"Why this is here" (template).** e.g. "Teaches SQL and Excel – the role weights them 4–5 and you rated them Basic." / "Required before PL-300." / "Practice for interviews (you asked for interview prep)." Built from ids, names and numbers only.

### 3. Optional AI (explanation text only) – in v1 (owner, Q1)
- Off unless `FEATURE_PLAN_BUILDER_AI` is on and a free provider is available. With AI off, unavailable, over its cap or failing, the template lines (section 2, step 12) are shown and the builder works the same; the draft never waits on AI (the preview returns template text, and the AI text replaces it when it arrives). It may only rewrite the "why" lines and add a 2-sentence plan overview. Input: role title, skill names with levels and weights, item titles and providers, hours. **Never** sent: names, CV text, role titles the user typed (`rolesHeld.title`), job post text, or any free-text answer. It passes through `buildSafeRequest` (redact + assert).
- The output replaces text only; item ids, order, hours, cost and links always come from `buildPlan`. Output that names an item, number or skill not in the input is discarded (template kept). Runs **only when the user presses "Explain with AI"** on the draft step (ADR 004: AI improves template text when the user asks), never on each preview re-run. Per-user daily cap and an app-wide daily cap (`AI_PLAN_EXPLAIN_DAILY_TOTAL`, like `AI_CV_TAILOR_DAILY_TOTAL`).
- Needs a new AI purpose `plan_explain`: an additive migration widening **both** `ai_usage_daily_purpose_check` and the `ai_cache` purpose check from 0010 (generated names to be verified in a migrated database, as 0017 did; 0017 left `ai_cache` unchanged), `rnd` first, then `prod`; and a `plan_explain` entry in `CACHE_TTL_MS` (`apps/api/src/ai/cache.ts`; 7 days). Endpoint: `POST /api/v1/plans/build/explain` with `{ draftHash, request }`; the server re-runs `buildPlan`, builds the allowlisted input itself (the client sends no text) and returns `{ lines: Record<taskId, string>, overview }` or 503 `ai_unavailable` (the web keeps the templates). The answer is cached by the gateway under `cacheKey(SafeAIRequest)`; because the server rebuilds the same allowlisted request from the same draft, the same draft hits the same entry. The lines are saved into task `notes` only when the user presses "Start this plan" while they are shown (`useAiExplanations: true`); otherwise templates are saved.

### 4. API (`apps/api/src/modules/plan-builder`, flag `FEATURE_PLAN_BUILDER`, default off; off → 404)
New endpoints; the write reuses the import service rather than `/plans/import`, so the server — not the client — decides the tasks, links and cost.

| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/api/v1/plans/build/explain` | `{ request: BuildRequest, draftHash }` | 200 `{ lines, overview }`; 503 `ai_unavailable`, 429 caps; 404 when `FEATURE_PLAN_BUILDER_AI` is off (section 3) |
| POST | `/api/v1/plans/build/preview` | `BuildRequest` | 200 `BuildDraft` (plan file, items with flags/cost/why, summary, warnings, `draftHash`). **Saves nothing.** 400 strict schema, 422 unknown role/skill/catalog id or deadline ≤ start |
| POST | `/api/v1/plans/build` | `{ id: uuid, request: BuildRequest, draftHash, replacesPlanIds: uuid[], useAiExplanations?: boolean }` | If the `id` exists, answers by the request-body hash first (section 4.1, step 2). Otherwise re-runs `buildPlan`; if its hash ≠ `draftHash` → 409 `draft_changed` (catalog or inputs changed; the web re-previews). Else, in **one transaction** (order in section 4.1: per-user lock, idempotency check, active-set check, archive, insert), writes through the import service with `created_from = 'builder'`, status `active`, and `summary.targetRoleIds` + `summary.builderVersion`. Same `id` + same content → 200; different → 409 (import rules). With `useAiExplanations: true` the server rebuilds the explain request and reads only the cache (no provider call, never text from the client); on a miss, templates |
| POST | `/api/v1/plans/:id/restore` | `{ replacesPlanIds: uuid[] }` | Archived plan → `active`; the current active plan → `archived`; one transaction (section 4.1) |

`BuildRequest` (shared zod, `.strict()`; **no free text at all**, so no PII can enter): `targetRoleIds` (1–2), `extraSkillIds` (≤ `target_skills.max`, today 5), `skillLevels: Record<skillId, 0..3>` (≤ 60), `startDate`, `deadline`, `weekPattern` (`WeekPatternSchema`), `budget {mode, amount? (required when mode = limit), maxItemPrice?}` (USD), `certPreference`, `interviewPrep`, `certificateOptIns` (≤ 10 catalog ids), `examDates` (≤ 10 `{catalogId, date, start}`), `mustInclude` / `exclude` (≤ 30 catalog ids each), `priorityOverrides: Record<catalogId, 'core'|'optional'>`. No `userId`; the user is `request.accountId`. Terms guard, rate limit as other writes. `docs/api-plan-builder.md` + regenerated OpenAPI and web client.

Why not plain `/plans/import`: it would let the web assemble tasks and prices (spec 12.3 forbids business logic in the frontend; spec 3.0 wants cost recalculated by the backend) and would record `created_from = 'import'`.

### 4.1 Archiving the old active plan (owner, Q3)
**How plan status works today (read on `rnd`):** `plans.status` allows `draft`, `active`, `archived`, `done` (0004), but **no endpoint changes it** and nothing reads it except calendar sync. Import creates `active` plans by default (`draft` is allowed in the body), so a user can have several active plans; the web lists every plan regardless of status (newest first, `PlanSwitcher`). Calendar sync already treats the newest `active` plan as primary and removes the future app events of other plans through the write guard (`removeOtherPlanEvents`), including archived ones. **There is no restore and no read-only rule today.**

**Decision:**
- **Which step archives:** `POST /plans/build`, inside the same `db.withUser` transaction as the plan insert, in this order:
  1. **Per-user lock:** `pg_advisory_xact_lock(hashtextextended(advisoryKey(ctx, 'active-plan', userId), 0))` (the pattern in `modules/days/repository.ts`). A `select … for update` on active plans alone locks nothing when none is active, so two concurrent builds could both succeed. `/plans/import` and `/plans/:id/restore` take the same lock, so a build cannot race an import either.
  2. **Idempotency first:** for a build the stored hash is a hash of the **request body** (`request`, `draftHash`, `useAiExplanations`), recorded in the `plan.imported` event. If a plan with this `id` exists, that hash is compared **before** `buildPlan` is re-run and before the `draftHash` comparison: same body → **200** with the stored plan, nothing re-built or archived again; other body → 409. So a catalog deploy, a different AI-cache result or a changed active set between the two calls cannot turn a retry into 409. Only a new `id` goes on to re-run `buildPlan` and compare `draftHash` (→ 409 `draft_changed`).
  3. **Active-set check:** `select id from plans where user_id = $1 and status = 'active'`; if that set is not exactly `replacesPlanIds` (≤ 10; empty when there is no active plan) → 409 `active_plan_changed`, nothing written (the web re-reads the list and shows the dialog again with the right names).
  4. **Archive:** `update plans set status = 'archived', updated_at = now()` for those ids, and a `plan.archived` event (`{ by: 'plan_builder', replacedBy: <new id> }`) per plan.
  5. **Insert** the plan as `importOnce` does (plan, week pattern, overrides, tasks, `plan.imported`).
  - Any failure rolls back all of it. The existing unique-violation retry of `importPlan` re-runs the whole sequence, and the retry takes the step 2 path. This is a **refactor of `importOnce`** (lock, a hook between the idempotency check and the insert, `createdFrom`), not a small change; the existing import tests must pass unchanged. If several plans are active (possible today through import), the dialog lists all their names and all are archived.
- **What the user sees first:** the confirm dialog in section 1 step 5, naming the plan(s) from `GET /plans`. No dialog when there is no active plan.
- **Read-only (owner, Q13):** archived plans stay visible in the plan switcher, marked "Archived", and their history (logs, reviews, practice) is kept. A helper `requireWritablePlan(ctx, userId, planId)` in `modules/plans` locks the plan row in the write's own transaction (`lockPlan`, `for no key update`, as `repository.ts` already does) and answers 409 `plan_archived` when the status is `archived`. It rejects **only** `archived`: import creates `draft` plans today and they stay writable; `done` is not set by any code today and stays writable until a feature sets it (Q13). Route classes:
  - refused on an archived plan: `PUT week-pattern`, `PUT start-date`, `PUT`/`DELETE day-overrides/:date`, `PATCH`/`DELETE tasks/:taskId`, `POST tasks/:taskId/logs`, `POST tasks/:taskId/complete|reopen|skip` (complete also creates `cv_update` tasks), `POST tasks/:taskId/practice/sessions` (new session), `PUT practice/context`, `POST practice/sessions/:id/messages`, `POST days/:date/start|end`, `PUT days/:date/review`, `POST suggestions/:id/accept|reject`;
  - allowed: `DELETE /plans/:id`; `POST /plans/:id/restore` (it is how an archived plan leaves the archive); the read-only POSTs that save nothing (`schedule/preview`, `suggestions/:id/preview`); `practice/sessions/:id/finish`, `/abandon` and `/feedback` for a session that already exists, so a session open at archive time can be closed and its result kept.
  - **Server-internal writes are allowed and must not be guarded:** `GET /plans/:planId/progress` runs `rolloverIfScheduled` (day snapshots); calendar sync writes `calendar_event_links` / `calendar_locked_blocks` while it removes the archived plan's events; the `plan.archived` event itself is written to the archived plan. `requireWritablePlan` is called only from the user-facing write routes above, never from these paths.
  - A route-table test enumerates every `POST/PUT/PATCH/DELETE` route under `/plans/:id` or `/plans/:planId` and asserts its class (409 or allowed) on an archived plan, so a new route cannot skip the decision.
- **Reversible (smallest safe option):** `POST /api/v1/plans/:id/restore` (behind the same flag) with the same lock-check-swap in one transaction: the archived plan becomes `active`, the current active plan(s) become `archived`, events `plan.restored` / `plan.archived`. Confirm dialog: "**<current>** will be archived and **<restored>** becomes your plan again. Tasks are rescheduled from today." It takes the same per-user lock and uses the same active-set check (`replacesPlanIds`). The engine already schedules from today, so a restored plan with past dates needs no special case; its finish date may move (shown in the change summary). Only `archived → active` is allowed (`done` and `draft` are out of scope). A retried restore returns **200** when the plan is already the only active plan (checked after the lock, before the active-set check), so a retry never answers 409.
- **Calendar:** calendar sync runs after a write only for routes matching `RESCHEDULING_ROUTE` (`apps/api/src/app.ts`); WP-2 adds `/plans/build` and `/plans/:id/restore` to it, with a test. The sync then removes the archived plan's future events from the app's own calendar and writes the new plan's (existing `removeOtherPlanEvents`; write guard and `calendar.app.created` scope unchanged).
- **Import path unchanged:** `/plans/import` keeps creating `active` plans without archiving (it is the owner's tool); the spec's "one active plan" is met for builder-created and restored plans. It takes the per-user lock only.
- No migration: the status values exist, events accept any dotted type. WP-2 verifies the app role may `update plans.status` in a migrated database (it already updates `start_date`).

### 5. Data needs and catalog gaps (measured on `rnd`, 2026-11-12)
| Gap | Effect | Proposal |
|---|---|---|
| No exam duration field; `cert_exam.est_hours` mixes prep and exam (e.g. `capm` 60 h); durations exist only in `notes` ("70 minutes") | A 60 h non-splittable task cannot be placed | Owner decision Q11: no new catalog field. Every exam block is 2 h with "Needs check: exam length"; preparation = `est_hours − 2` |
| 50 of 178 items `url_verified: false`; 104 `price_verified: false`; 31 `url: null`; 15 `price: null` | Many drafts carry "needs check" | Shown as such, never as verified; `url: null` never chosen |
| Only 18 items have `free_alternative_ids`; 45 paid items have none | Budget swaps often impossible | Say "no free equivalent in the catalog"; extending the data is a catalog task |
| `interviewing` is taught by no course (practice templates only); 12 role skills have no free item with a link (e.g. `git`, `software-testing`, `ux-basics`, `windows-m365-admin`); 10 skills have ≤ 1 course or exam item (practice templates not counted) | Free-only plans leave gaps | Listed as "gaps the catalog cannot fill", never padded with invented items |
| `skill_depth` is empty everywhere; 33 items `level: unspecified` | Level matching is coarse (unspecified = beginner) | Accept for v1 |
| Thin roles: Bookkeeper (3 core), Technical Writer (3), L&D Coordinator (2 core, **0 free-only**) | Short or empty free plans | Warning on the draft; catalog extension later |
| One subscription has no price and no period; one is yearly without a group | Cost rule edge cases | Unit tests cover both; shown as "check price" |

### 7. Risks
- **Bad advice from thin data:** a rule-based plan can look authoritative. Mitigation: "estimates", "needs check" badges, explicit gaps, and the draft is always reviewed before creation.
- **Over-trust in levels from the CV matcher** (ADR 015 never sets 3, never 0). Mitigation: step 2 shows the source of every level and lets the user change it.
- **Cost surprises** with subscriptions and unverified prices. Mitigation: "estimated" label, per-item price status, subscription months shown.
- **Catalog drift between preview and create.** Mitigation: `draftHash` → 409 → re-preview.
- **Archiving surprises the user.** Mitigation: the confirm dialog names the plan, archived plans stay readable, and restore exists. **Missed write route on an archived plan.** Mitigation: the route-table test. **Bundle size:** `catalog.json` (~178 items) in the API is fine; the web must not import the catalog module eagerly (lazy route chunk, measured in WP-3).

## Consequences
- Every plan the builder makes is reproducible from its inputs and the catalog version, works with AI off, and holds only catalog links (verified ones) or none.
- The plans module gains `createdFrom` on the import service, an archive/restore step and the `requireWritablePlan` guard on plan-scoped writes. One migration in v1 (0019, the `plan_explain` AI purpose; 0018 is the calendar cron PR #113).
- Catalog quality becomes visible to users (badges, gaps); extending the catalog is the main lever for better plans.
